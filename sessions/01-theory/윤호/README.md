# 윤호 — Docker의 이미지와 레이어에서 Linux 커널 원리까지

## 탐구 목표

**Docker의 이미지·레이어·컨테이너 파일시스템을 먼저 이해하고, 이를 실행하는 프로세스와 Linux의 격리·자원 관리 원리로 내려갑니다.**

전체 흐름은 이미지와 Dockerfile → 레이어와 빌드 → 컨테이너의 쓰기 영역과 데이터 수명 → 프로세스와 실행 → namespace·cgroup → 선택적인 커널 소스 추적입니다.

## 첫 회차 범위

첫 회차는 아래 1·2단계의 Docker 기본 구조와 동작 실험에 집중합니다. 먼저 이미지의 레이어와 컨테이너별 변경 사항을 설명하고, 중지·삭제·재생성 시 데이터 상태를 확인합니다.

커널 탐구는 그다음 단계입니다. PID namespace·cgroup 실험을 첫 회차 완료 조건으로 두지 않습니다. 더 진행할 여유가 있으면 연결 질문을 만들고 후속 회차에서 이어갑니다.

## 1단계 — 이미지·Dockerfile·레이어

### 질문

- Docker가 해결하려는 실행 환경의 문제는 무엇인가?
- Dockerfile, 이미지, 컨테이너는 각각 어떤 역할을 하는가?
- 이미지를 레이어로 구성한다는 것은 무엇이며, 왜 이런 구조를 사용하는가?
- 이미지의 파일시스템 변경과 실행 설정 같은 메타데이터는 어떻게 다른가?
- 빌드 캐시는 어떤 조건에서 재사용되며, 레이어 구조와 어떻게 연결되는가?

이미지 레이어는 파일시스템 변경을 담으며, 여러 레이어를 합쳐 하나의 파일시스템 관점으로 사용합니다. 생성된 이미지 레이어와 실행 중 생기는 변경을 구분해 이해합니다. [Docker 이미지 레이어 안내](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/)

### 실험 A — 작은 이미지 만들고 살펴보기

1. 작은 Dockerfile에 `FROM`, `COPY`, `RUN`, `CMD` 등을 사용해 파일과 실행 명령을 정의합니다.
2. 각 지시문이 빌드 중 하는 일과 컨테이너 실행 시 하는 일을 먼저 예상합니다.
3. 이미지를 빌드하고 `docker image history`와 `docker image inspect`로 생성 이력·파일시스템 레이어 정보·실행 설정을 살펴봅니다.
4. Dockerfile의 줄 수, history의 항목 수, 실제 파일시스템 레이어 수가 항상 같은지 확인합니다.
5. 선택적으로 같은 조건에서 다시 빌드한 뒤 입력 파일 하나를 수정해 빌드 로그의 캐시 사용 차이를 관찰합니다. 캐시가 사용되지 않았다면 조건과 원인을 조사합니다.

첫 실험은 빌드 최적화보다 각 구성 요소의 역할을 이해하는 데 집중합니다. 빌드 캐시와 컨테이너의 쓰기 영역을 같은 개념으로 혼동하지 않습니다.

## 2단계 — 컨테이너 파일시스템과 수명주기

### 질문

- 같은 이미지로 여러 컨테이너를 만들면 무엇을 공유하고 무엇이 달라지는가?
- 컨테이너에서 파일을 추가·수정·삭제하면 변경은 어디에 반영되는가?
- 이미지의 읽기 전용 레이어와 컨테이너의 쓰기 영역은 어떤 관계인가?
- 중지 후 재시작과 삭제 후 새 컨테이너 생성은 어떻게 다른가?
- 볼륨과 바인드 마운트를 사용하는 이유는 무엇인가?

컨테이너의 쓰기 영역은 컨테이너별로 존재하며, 볼륨 등의 별도 저장 영역과 구분됩니다. 컨테이너 수명주기와 데이터 수명주기를 나눠 살펴봅니다. [Docker 저장소 문서](https://docs.docker.com/engine/storage/)

### 실험 B — 파일 변경과 데이터 수명 비교

1. 같은 이미지로 컨테이너 두 개를 실행합니다. 먼저 별도 볼륨·바인드 마운트 없이 진행하고, 이미지에 선언된 볼륨 등 저장 관련 설정도 확인합니다.
2. 한쪽에서 파일을 추가하거나 수정한 뒤, 다른 컨테이너와 원본 이미지로 만든 새 컨테이너에도 변경이 보일지 예상하고 확인합니다. `docker diff`를 보조 관측으로 사용할 수 있습니다.
3. 파일을 만든 컨테이너를 중지하고 다시 시작해 프로그램 실행 상태와 파일 상태를 각각 확인합니다. 이 단계는 컨테이너를 자동 삭제하는 설정 없이 진행합니다.
4. 해당 컨테이너를 삭제하고 같은 이미지로 새로 만든 뒤 파일 상태를 확인합니다.
5. 여유가 있으면 명시적인 named volume을 연결해 같은 과정을 비교합니다. 볼륨 자체를 삭제하는 작업과 컨테이너만 삭제하는 작업을 구분합니다.

### 커널 탐구로 이어질 질문

- 여러 레이어가 어떻게 하나의 파일시스템처럼 보이는가?
- Copy-on-write는 어떤 문제를 해결하는가?
- 현재 환경의 스토리지 드라이버 또는 snapshotter는 무엇인가? OverlayFS를 사용하는 환경이라면 그 원리는 무엇인가?
- 파일시스템을 준비한 뒤 실제로 실행되는 프로세스는 무엇인가?
- 파일시스템 구성을 합치는 기능과 mount namespace의 역할은 어떻게 다른가?

첫 회차부터 실제 저장 백엔드 내부를 모두 추적할 필요는 없습니다. 기본 동작을 설명한 뒤 구현 원리로 확장하며, 모든 Docker 환경이 같은 저장 백엔드를 쓴다고 가정하지 않습니다.

## 기본 실험 환경과 기록

첫 1·2단계는 Docker Desktop 또는 Linux의 Docker Engine에서 진행할 수 있습니다. 호스트 OS, Docker 버전과 context, 이미지·Dockerfile·실행 명령, 볼륨 설정을 기록합니다. 커널 상태를 직접 확인할 환경은 3단계로 넘어갈 때 준비합니다.

AI는 개념 설명·질문·실험 준비에 활용합니다. 핵심 내용은 공식 자료와 직접 관찰로 확인하며, 실제 결과를 보기 전에 예상을 남깁니다.

## 3단계 — Linux 커널 기능으로 내려가기

기초 실험을 설명할 수 있게 된 뒤 진행합니다. 아래는 후속 탐구 계획이며 첫 회차 필수 범위가 아닙니다.

### 커널 탐구 환경

Linux 컨테이너를 대상으로 합니다. Linux 호스트에서 `/proc`와 cgroup 상태를 직접 관찰할 수 있는 환경을 사용합니다. 별도의 Linux VM에 Docker Engine을 설치한 환경도 가능합니다.

Docker Desktop의 Linux 컨테이너는 Linux VM 안에서 실행되므로, 이 문서의 'Linux 호스트'는 컨테이너를 실행하는 그 Linux 환경을 뜻합니다. macOS 터미널의 프로세스 번호와 Linux VM 안의 PID를 그대로 비교하지 않습니다. Desktop을 사용한다면 어느 관찰 지점에 접근할 수 있는지 먼저 확인합니다. [Docker Desktop 실행 환경](https://docs.docker.com/desktop/features/networking/)

기록할 항목:

- 호스트 OS와 Linux 커널 버전, Docker Engine / Desktop 여부
- Docker 버전과 context, rootless 여부
- cgroup v1/v2 및 cgroup driver, 실행 이미지와 명령어
- CPU 개수, 컨테이너에 설정한 제한, 관측 위치

`docker info`로 환경을 확인합니다. 아래 cgroup 파일명은 v2 기준이며, v1 환경에서는 해당 버전의 문서로 조정합니다. Docker 설정에 따라 실제 cgroup 경로도 달라지므로 고정 경로를 추측하지 않습니다. [Docker Runtime metrics](https://docs.docker.com/engine/containers/runmetrics/)

### 커널 탐구 흐름

| 단계 | 할 일 | 남길 증거 |
|---|---|---|
| 예상 | 컨테이너 안팎의 PID와 CPU 제한 결과를 예상 | 초기 설명 |
| 개념 | 프로세스·namespace·cgroup을 자료와 AI로 학습 | 자신의 말로 쓴 역할 구분 |
| 관찰 | Docker로 실행하고 커널 인터페이스를 확인 | PID·namespace 식별자·cgroup 경로와 값 |
| 검증 | CPU 부하를 제한 전후로 비교 | 실행 조건·측정 시간·관측값 |
| 설명 | 설정과 커널 기능, 결과를 연결 | 수정한 설명과 남은 질문 |

### 커널 실험 1 — PID namespace와 프로세스

1. 단순하게 계속 실행되는 프로세스를 가진 실험용 컨테이너를 실행합니다.
2. 컨테이너 내부에서 프로세스 목록을 확인하고, `docker inspect`의 `State.Pid`로 Linux 호스트 관점의 컨테이너 초기 프로세스 PID를 찾습니다.
3. Linux 호스트의 `/proc/<PID>/status`에서 `NSpid`를 살펴보고, 내부에서 관찰한 PID와 관계를 설명합니다. 관측 위치에 따라 보이는 계층이 달라질 수 있습니다.
4. `/proc/<PID>/ns/pid`와 호스트 셸의 `/proc/self/ns/pid` 링크를 비교합니다. 같은 호스트 커널 안에서 namespace 식별자가 같은지 다른지 확인합니다.
5. 컨테이너 초기 프로세스를 종료하거나 컨테이너를 중지하고 실행 상태 변화를 관찰합니다.

PID namespace가 프로세스 ID의 관점을 분리한다는 설명을 실제 출력으로 뒷받침합니다. `/proc/<PID>/ns/`의 다른 항목은 목록을 살펴보되 모두 실험할 필요는 없습니다. [Linux namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)

### 커널 실험 2 — cgroup과 CPU 제한

1. CPU 부하를 만드는 작은 작업을 실험용 컨테이너에서 정해진 시간 동안 실행합니다. 예를 들어 단일 작업을 10~20초 관찰하며, 같은 작업을 제한 전후에 비교합니다.
2. Docker의 CPU 제한 옵션(예: `--cpus=0.5`)을 설정하고 어떤 결과가 나올지 예상합니다.
3. Linux 호스트에서 컨테이너 초기 프로세스의 `/proc/<PID>/cgroup`을 읽고, 해당 호스트의 cgroup 마운트와 연결해 실제 디렉터리를 찾습니다.
4. v2 환경에서는 `cpu.max`의 quota와 period, `cpu.stat`의 사용량과 throttling 관련 값의 변화를 확인합니다. `docker stats`는 보조 관측으로 사용합니다.
5. 옵션 값만 확인하는 데서 끝내지 않고, 제한 전후의 관측 차이가 설정과 어떻게 연결되는지 설명합니다.

CPU 사용 비율은 측정 구간과 부하, 상위 cgroup의 제한에도 영향을 받을 수 있습니다. 순간 수치가 특정 값과 정확히 같아야 한다고 가정하지 않습니다. CPU 대역폭 제한과 특정 CPU에 배치하는 것은 별개의 질문으로 구분합니다. [Linux cgroup v2 문서](https://docs.kernel.org/admin-guide/cgroup-v2.html)

실험은 종료 시간이 정해진 작은 부하로 수행하고, 관찰한 호스트의 기존 cgroup 설정을 직접 바꾸지 않습니다.

## 추가 탐구 — 필요한 것만 선택

### namespace 확장과 Docker 없는 재현

Mount·UTS·Network·User namespace 중 하나를 선택해 다루는 대상을 확인합니다. Linux 실험 환경에서 `unshare`나 `nsenter`로 작은 재현을 시도할 수 있습니다. `unshare` 실험 하나가 Docker 전체를 구현한 것과 같지는 않습니다. 권한이나 rootless 설정 때문에 확인하지 못했다면 그 조건을 기록합니다.

### 메모리 제한

cgroup v2의 `memory.max`, `memory.current`, `memory.events`를 살펴봅니다. 메모리 압력·회수·OOM과 프로세스 종료를 구분해 질문을 세웁니다. 재현한다면 작은 메모리 제한이 걸린 실험용 컨테이너 안에서만 수행하고 관련 이벤트와 종료 상태를 함께 확인합니다.

### 커널 소스 추적

실험한 Linux 커널 버전에 맞는 소스에서 PID namespace 또는 cgroup CPU 제어의 관심 경로 하나를 따라갑니다. 사용자 인터페이스와 내부 자료구조·함수의 관계를 적으며, 소스 전체를 읽는 것을 목표로 하지 않습니다. 실행 커널과 읽은 소스 버전이 다르면 차이를 표시합니다.

### 첫 회차 — Docker 기본 구조

- Dockerfile·이미지·컨테이너의 역할을 자신의 말로 설명합니다.

- 빌드와 파일 변경 실험에서 예상·결과·이유를 기록합니다.
- 컨테이너 중지·삭제·재생성의 차이를 데이터 상태와 연결해 설명합니다.

### 후속 커널 탐구

- namespace의 환경 분리와 cgroup의 자원 관리를 구분합니다.
- PID namespace와 CPU 제한에 대해 Docker 설정·커널 인터페이스·관찰 결과를 연결합니다.
- 필요하면 파일시스템 구현과 커널 소스를 더 살펴봅니다.

이 문서는 탐구 계획이며 실험은 아직 수행하지 않았습니다. 확인한 범위와 남은 질문을 구분해 다음 탐구로 이어갑니다.
